# Residual Conflict / Failure Classes NOT Named by the Owner

**Scope.** Owner's stated residual set: (1) tombstone-vs-promotion, (2) supersession cycles / dangling targets, (3) epoch rollback.
Everything below is *outside* that set, and every entry is backed by a primary spec, paper, vendor postmortem, or official docs page that I fetched and read directly. Anything I could not source is listed under "Discarded / Unsourced".

**System under review (as described):**
- Two stores: Swift/Core Data (canonical) + Rust/SQLite (local-first replica).
- Identity = `(contentDomain, contentDigest)`; digest = H(NFC-normalized text ‖ RFC 8785 canonical metadata).
- Digest EXCLUDES: embeddings, enrichment, `createdAt`, transaction sequence.
- Merge on digest match: `min(createdAt)`, `union(tags)`, `append(sightings)`.
- One-directional read-only replica; async idempotent promotion keyed `(epoch, monotonic sequence)`.
- Ed25519-signed bundles; tombstones; supersession references a record digest.

## Findings — Confirmed residual conflict/failure classes

Ordered roughly by severity for this design (silent identity corruption first).

### A. NFC-before-JCS is a spec violation that makes your canonical bytes non-reproducible
**How it bites:** RFC 8785 §3.1 states flatly that "all components involved in a scheme depending on JCS **MUST preserve Unicode string data 'as is'**" and that "parsed JSON string data MUST NOT be altered during subsequent serializations" [6]. Your digest is defined as NFC-normalized text *plus* RFC 8785 canonical metadata. If any metadata **string value or key** is NFC-normalized at any point in the pipeline (before or after canonicalization), you are outside the JCS contract: two implementations that disagree about *where* the NFC step happens produce different canonical bytes, hence different digests, hence two "records" that are semantically identical. Worse, this is order-dependent — normalize-then-canonicalize ≠ canonicalize-then-normalize whenever normalization changes UTF-16 code-unit ordering of property names (see C).
**Primary source:** https://www.rfc-editor.org/rfc/rfc8785#section-3.1 [6]

### B. Unicode version skew between Swift/Foundation (OS-supplied ICU) and Rust (crate-pinned UCD) — unassigned/PUA-adjacent codepoints
**How it bites:** Strong Normalization Stability is guaranteed *only* for strings whose characters are assigned in **both** Unicode versions involved [1][3]. Text containing a codepoint assigned in Unicode 16 but unassigned in the version bundled with a given macOS release (Foundation `precomposedStringWithCanonicalMapping` uses the OS ICU) will be left alone by the older side and possibly composed by the newer side. The Rust side pins its UCD via a compile-time `UNICODE_VERSION` constant [5], so the two sides drift on independent release cadences — an OS update or a `cargo update` silently changes your record identity function. Apple's own TN1150 states the general rule for exactly this situation: "An implementation **must not** use the Unicode utilities implemented by its native platform... **This is rarely the case. Platform algorithms tend to evolve with the Unicode standard**" — and documents the real-world break: macOS 8.1–10.2.x used Unicode 2.1 decompositions, 10.3+ used Unicode 3.2 [4].
**Fix precedent (also unnamed by owner):** UAX #15 §12 defines the **Normalization Process for Stabilized Strings (NPSS)**, which is NFC *plus* "The process must be aborted with an error if the string contains any code point with the property value General_Category=Unassigned" [2]. Your design has no such abort, so it silently produces unstable digests instead of rejecting the input.
**Primary sources:** https://unicode.org/policies/stability_policy.html [1] · https://unicode.org/reports/tr15/#Normalization_Process_for_Stabilized_Strings [2] · https://developer.apple.com/library/archive/technotes/tn/tn1150.html [4]

### C. JCS property sorting is UTF-16 code-unit order; Rust strings are UTF-8/codepoint order
**How it bites:** RFC 8785 §3.2.3 requires property names to be sorted "as arrays of **UTF-16** code units" and explicitly warns that "sorting of data encoded in UTF-8 or UTF-32 would also work, but the outcome... would **differ and thus be incompatible** with this specification" [7]. The divergence set is exactly: keys containing supplementary-plane characters (U+10000+, e.g. emoji) versus keys containing U+E000–U+FFFF (private-use area, CJK compatibility, Hebrew presentation forms). The spec even ships the canonical failing example: `"\ud83d\ude00"` (grinning face, U+1F600) must sort **before** `"\ufb33"` (U+FB33) under UTF-16, but **after** it under codepoint order [7]. A naive Rust `BTreeMap<String, _>` / `sort()` gives codepoint order. That is a silent cross-store digest split, and it also interacts with (A): PUA is the same region where Unicode assignment stability arguments break down.
**Primary source:** https://www.rfc-editor.org/rfc/rfc8785#section-3.2.3 [7]

### D. Duplicate / colliding property names after normalization — I-JSON's "duplicate" is codepoint identity, not canonical equivalence
**How it bites:** I-JSON defines duplicate as names that are "**identical sequences of Unicode characters**" after unescaping [10] — a *byte/codepoint* test. Two keys that are canonically equivalent but not identical (`"café"` NFC vs `"cafe\u0301"` NFD) are **legal** I-JSON. But if your app NFC-normalizes keys (see A), those two legal-and-distinct keys **collapse into a duplicate**, at which point you are in RFC 8259 §4 territory: "the behavior of software that receives such an object is **unpredictable**. Many implementations report the last name/value pair only. Other implementations report an error or fail to parse." [9] Swift's `JSONSerialization`/`Codable` dictionary decode and Rust's `serde_json::Map` do not have the same last-wins/first-wins/error policy. Result: silent key loss on one store, error on the other, or two different canonical byte strings.
**Primary sources:** https://www.rfc-editor.org/rfc/rfc7493#section-2.3 [10] · https://www.rfc-editor.org/rfc/rfc8259#section-4 [9]

### E. JCS number serialization + string-subtype round-tripping
**How it bites:** JCS constrains numbers to IEEE-754 doubles serialized per ECMA-262 §7.1.12.1, and mandates termination on NaN/Infinity [8]. Swift's `Codable`/`JSONSerialization` and Rust's `serde_json` (which can be built with `arbitrary_precision`, or emit `1e+30` vs `1.0e30`) do not natively produce ECMAScript number strings; getting them to agree requires a Ryu/V8-compatible shortest-repr formatter on **both** sides. Additionally, RFC 8785 Appendix E documents that stream/schema-based parsers that convert string subtypes on the fly (timestamps, big integers) yield *different* canonical output for the same source document — "presumably making an application depending on JCS fail" [8]. A `createdAt`-adjacent ISO-8601 string that Swift's `JSONDecoder.dateDecodingStrategy` re-serializes as `2019-01-28T07:45:10.000Z` while Rust keeps `2019-01-28T07:45:10Z` is a digest split.
**Primary source:** https://www.rfc-editor.org/rfc/rfc8785#section-3.2.2.3 and Appendix E [8]

### F. Stream-Safe Text Format divergence (UAX15-D4)
**How it bites:** UAX #15 §13 defines Stream-Safe Text Format, which **inserts U+034F CGJ** after 30 consecutive non-starters [28]. This is not part of NFC, but ICU-based pipelines and the Rust crate expose it as separate opt-in machinery (`StreamSafe` iterator [28]). If either side applies stream-safe processing (or an intermediate transport/normalizer does) and the other does not, adversarial or pathological combining-mark input produces different bytes ⇒ different digests for identical text. This is a cheap DoS/identity-forking vector against a content-addressed store.
**Primary source:** https://www.unicode.org/reports/tr15/#UAX15-D4 [28]

### G. `union(tags)` is a G-Set: tag removal is structurally impossible, and adding removal later is a breaking migration
**How it bites:** Shapiro et al. §3.3.1: a Grow-Only Set "supports operations **add and lookup only**" — the "simplest solution is to avoid remove altogether" [11]. Your merge rule is exactly a G-Set. Consequences the owner has not named: (i) a mistagged or PII-bearing tag can never be retracted — a compliance/GDPR-erasure problem, not just a UX one; (ii) any future "untag" feature must be a 2P-Set or OR-Set, and 2P-Set has the additional documented anomaly that an element "may be added and removed, but **never added again thereafter**" [11]; (iii) an OR-Set retrofit requires per-add unique tags, which changes the on-wire bundle format and is therefore an epoch-level migration coupled to (K).
**Primary source:** https://inria.hal.science/inria-00555588/document §3.3.1 [11]

### H. `append(sightings)` is an unbounded op-log with no compaction horizon
**How it bites:** Shapiro et al. report from practice that CRDTs "tend to become **inefficient over time, as tombstones accumulate**", and that avoiding unbounded growth requires GC using "a weak form of synchronisation" which **may block** and is not always live [12]. Kafka's design doc makes the same point about append-only logs: "the **log will grow without bound even for a stable dataset**" [13]. Your `sightings` list is per-record, monotone, and merged by concatenation across two stores — so a frequently-re-observed record grows without bound in *both* Core Data and SQLite, with no `min.compaction.lag.ms` / `delete.retention.ms` analogue. Note the second-order bite from Kafka: once you *do* add compaction, you inherit a **retention horizon**, and any replica that lags longer than that horizon "can miss delete markers" [13] — i.e. compaction converts an unbounded-growth bug into a correctness bug unless the promotion lag bound is enforced.
**Primary sources:** https://inria.hal.science/inria-00555588/document §4 [12] · https://kafka.apache.org/35/design/design/ [13]

### I. `min(createdAt)` is an irreversible LWW-style clock sink — one bad clock is permanent
**How it bites:** `min` over a lattice is monotone and therefore **irreversible**: a device whose wall clock reads 1970 (or is stepped backward by NTP) contributes a `createdAt` that can never be corrected by any subsequent correct observation, and it propagates through every merge. Documented failure modes for the input clock: "Hardware wonkiness can push clocks **days or centuries** into the future or past", virtualization, missing NTP, "**Upstream NTP servers can lie**", NTP step corrections that "**jump the clock discontinuously**", and POSIX time being non-monotonic across leap seconds [15]. Cloudflare's leap-second postmortem is a concrete production instance: "The root cause of the bug... was **the belief that time cannot go backwards**", causing a Go service panic and ~0.2% DNS query failures for over an hour [16]. Your design has **no repair path**: unlike Cassandra's LWW (where a later, larger timestamp eventually wins), `min` means the *earliest wrong* value wins forever.
**Primary sources:** https://aphyr.com/posts/299-the-trouble-with-timestamps [15] · https://blog.cloudflare.com/how-and-why-the-leap-second-affected-cloudflare-dns/ [16]

### J. Non-identifying fields (embeddings, enrichment) — the "weak validator" problem
**How it bites:** RFC 9110 §8.8.1 is the canonical statement of this class: "if a resource has **distinct representations that differ only in their metadata**... then the origin server **needs to incorporate additional information in the validator** to distinguish those representations" [17]. A "weak validator" is precisely one where the owner chose "to group representations by some self-determined set of equivalency rather than unique sequences of data" [17]. Your digest is a weak validator over the full record. Concretely: two records with identical text but enrichment produced by **different model versions** (or different embedding dimensionality) are merge-eligible; your merge rule specifies behavior for `createdAt`, `tags`, and `sightings` but is **silent on enrichment and embeddings**, so the outcome is store-implementation-defined (Core Data relationship semantics vs SQLite upsert). That is a last-writer-wins on a field with no timestamp and no ordering — the worst case of the class. It also means model-version rollback is invisible: you cannot tell from the digest which enrichment generation you have.
**Primary source:** https://www.rfc-editor.org/rfc/rfc9110#section-8.8.1 [17]

### K. Hash agility: no algorithm identifier, and supersession/signatures are digest-typed
**How it bites:** Your `contentDigest` is a bare value with no algorithm tag, and **supersession references a record digest** — so the reference graph is typed by the hash function. Git's transition doc shows the real cost of retrofitting this: a repo-format extension that makes older clients "**die instead of** trying to operate"; a persistent **bidirectional translation table** between old and new names, verified by fsck; translation on every fetch/push; and — most relevant here — a **new signature field** `gpgsig-sha256` because the signed payload is the *new-hash* content, so old signatures do not carry over [18]. Applied to you: every Ed25519-signed bundle is a signature over old-digest-space content, and every supersession pointer is a dangling reference in new-digest-space. RFC 7696 (BCP 201) is the standing IETF guidance that agility must be designed in up front, with negotiation and coexistence [19]; multihash is the minimal mitigation — a varint hash-function code + length prefix so a digest is self-describing [20]. **You have none of these.**
**Primary sources:** https://git-scm.com/docs/hash-function-transition [18] · https://www.rfc-editor.org/rfc/rfc7696 [19] · https://github.com/multiformats/multihash [20]

### L. Ed25519 cross-implementation validity divergence between Swift (CryptoKit) and Rust (dalek/zebra) — the sharpest unnamed risk
**How it bites:** RFC 8032 §8.8 warns explicitly that cofactored vs cofactorless verification means "**in some applications it is undesirable for implementations to disagree about the exact set of valid signatures**" [21]. `ed25519-speccheck` measures exactly that disagreement across libraries [23]. From its published results table:
- **Apple CryptoKit** accepts vectors 0, 1, 2, 3, 11 (small-order A, small-order R, mixed-order, non-canonical A not-reduced-for-hash).
- **ed25519-dalek `verify_strict`** rejects 0, 1, 2 and 11.
- **ed25519-zebra** additionally *accepts* vectors 4, 5, 9, 10 that CryptoKit rejects.
- **libsodium** rejects 0, 1, 2.

So a bundle signed/accepted on the Swift canonical store can be **rejected** by the Rust replica (if it uses `verify_strict` or libsodium), or **accepted** by the Rust replica and rejected by Swift (zebra's vectors 4/5/9/10). In a one-directional replication design this manifests as **permanent, silent replica starvation**: the replica stops applying a bundle it cannot verify, with no back-channel to report it. Separately, RFC 8032 §8.4 says non-malleability rests entirely on "**the verification check that decoded S is smaller than l**" [22], and speccheck shows ed25519-java, python-ed25519, tweetnacl-js, ref10 and donna accepting out-of-range S (vectors 6/7) [23] — so **signature bytes are not a safe idempotency/dedup key for bundles**; an attacker can produce a second distinct byte string that verifies for the same message under some verifiers.
**Primary sources:** https://www.rfc-editor.org/rfc/rfc8032#section-8.8 [21] · https://www.rfc-editor.org/rfc/rfc8032#section-8.4 [22] · https://github.com/novifinancial/ed25519-speccheck [23] (paper: https://eprint.iacr.org/2020/1244)

### M. `(epoch, sequence)` idempotency does NOT survive an epoch change — duplicates at every epoch boundary
**How it bites:** This is precisely the Kafka idempotent-producer design, and KIP-98 states its limit in one sentence: "since each new instance of a producer is assigned a new, unique, PID, we **can only guarantee idempotent production within a single producer session**" [24]. Kafka needed a *separate, user-supplied, epoch-independent* `TransactionalId` to get cross-session identity, plus an explicit epoch bump used purely for **zombie fencing** [24]. Your promotion key is `(epoch, monotonic sequence)`: when the epoch changes, the sequence namespace resets, so operations in flight from epoch *n* are indistinguishable-from-new (or, if sequences restart at 0, actively **collide**) with epoch *n+1* operations. That is at-least-once, not exactly-once, across the boundary — an unnamed class distinct from "epoch rollback." The owner named rollback; the boundary itself is the bug. Note also Kafka's out-of-sequence handling: a gap "indicates that some messages have been lost, and **is fatal**" [24] — your design has no stated behavior for a sequence gap.
**Primary source:** https://cwiki.apache.org/confluence/display/KAFKA/KIP-98+-+Exactly+Once+Delivery+and+Transactional+Messaging [24]

### N. Two-store atomicity is a textbook dual-write; torn bundle application has no defined recovery
**How it bites:** "A dual write operation occurs when an application writes to two different systems... A failure in one of these operations might result in [inconsistent data]" [25]; "database transactions are usually scoped to the database" [26]. Core Data (SQLite-backed, but with its own managed-object graph and save semantics) and the Rust/SQLite store cannot participate in a common transaction. A bundle applied to N records that fails partway leaves the two stores in **different** states, and because your identity is content-derived rather than sequence-derived, there is no per-store watermark to resume from — the replica cannot answer "which subset of bundle B did I apply?" The documented remedy is the transactional outbox: write only to the local store (record + intent) in one transaction, and relay asynchronously [25][26]. Your promotion path currently has the intent *outside* the canonical transaction.
**Primary sources:** https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html [25] · https://www.confluent.io/blog/dual-write-problem/ [26]

### O. Tombstone GC horizon vs. replica lag ("zombie" resurrection) — a *refinement* of the named tombstone class the owner did not name
**How it bites:** The owner named "tombstone-vs-promotion." What they did not name is the **retention horizon** that any tombstone scheme must have once (H) forces compaction. Cassandra documents the exact failure: "If the tombstoned object has already been deleted from the rest of the cluster before that node recovers, Cassandra treats the object on the recovered node as **new data, and propagates it** to the rest of the cluster... called a **zombie**" [14], mitigated only by `gc_grace_seconds` (default 10 days) and by `only_purge_repaired_tombstones` [14]. Kafka states the same constraint from the consumer side: a consumer lagging more than `delete.retention.ms` "can **miss delete markers**" [13]. In your design, a replica that is offline longer than the tombstone retention window re-promotes a deleted record's digest and it is indistinguishable from a fresh sighting — because sightings append and `min(createdAt)` will happily accept the old value.
**Primary sources:** https://cassandra.apache.org/doc/stable/cassandra/managing/operating/compaction/overview.html [14] · https://kafka.apache.org/35/design/design/ [13]

### P. `contentDomain` string equality differs between the two stores (SQLite BINARY/NOCASE vs Foundation/ICU)
**How it bites:** Identity is `(contentDomain, contentDigest)`. The digest half is byte-safe; the **domain half is a string compared by each store's own collation**. SQLite's docs: "BINARY - Compares string data using **memcmp()**, regardless of text encoding"; "NOCASE... **only ASCII characters are case folded**. SQLite does not attempt to do full UTF case folding"; and, critically, "**any U+0000 characters in the string are considered string terminators for comparison purposes**" [27]. Core Data / `NSPredicate` string comparison is ICU-backed and honors locale/diacritic/case options. So `contentDomain = "Café"` vs `"CAFÉ"` vs `"cafe\u0301"` can be one key in one store and two (or three) in the other, and a domain containing an embedded NUL is truncated for comparison purposes in SQLite only. This forks record identity without any digest involvement.
**Primary source:** https://www.sqlite.org/datatype3.html [27]
