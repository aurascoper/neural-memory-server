# Documented Precedent for Three Conflict Classes in Signed Async Replication over Content-Addressed Stores

Scope: this is **not** a CRDT survey. The merge rule (min/union/append) is assumed commutative. What follows is documented precedent — named attacks/patterns, spec sections, paper titles with year + arXiv/DOI/URL, and the **stated cost** of each mitigation — for:

1. DELETE-vs-REINSERT / tombstone-vs-promotion (resurrection / "zombie" records)
2. DANGLING / UNRESOLVABLE REFERENCE and REFERENCE CYCLES in content-addressed DAGs
3. EPOCH ROLLBACK after key compromise + re-enrollment

Verification legend: `read` = I fetched and read the source text directly; `snippet` = I saw provider-returned text from the source but not the full document; `blocked` = could not fetch.

## Findings

### Class 1 — DELETE-vs-REINSERT / tombstone-vs-promotion (resurrection / "zombie")

**The pattern has a stable name in production systems: "zombie data" / "data resurrection."** Cassandra's own documentation uses exactly this word: without tombstones, a replica that missed the delete propagates the value back during anti-entropy repair, and "this would cause our data to be resurrected as a zombie even though it had been deleted" [1]. The wiki states the underlying asymmetry that makes this unavoidable in an eventually-consistent store: absence is indistinguishable from never-written, so a replica that still holds the value "will treat the replicas that did receive the delete as having missed a write update, **and repair them**" [2]. Riak's docs state the same in a worked node-A/B/C example and conclude "it isn't possible to determine which of two possible scenarios actually occurred: (1) the object was deleted on A & B but not on C, (2) the object was created on C but not on A & B" [6].

**Documented mitigation #1 — tombstone with a grace period, and its exact cost.** Cassandra's stated deletion condition for actually dropping a tombstone is three-part [1]: (a) tombstone age > `gc_grace_seconds`; (b) the compaction must include the SSTable holding the tombstone *plus all SSTables containing data older than the tombstone for that partition* — a partial compaction cannot safely drop it; (c) optionally `only_purge_repaired_tombstones`, which additionally requires the data to have been repaired. The stated failure condition is explicit: "If a node remains down or disconnected for longer than `gc_grace_seconds`, its deleted data will be repaired back to the other nodes and reappear in the cluster" [1]. The cost is therefore: **unbounded tombstone accumulation until a full-enough compaction, plus a hard operational SLA that anti-entropy repair must complete within `gc_grace_seconds` on every replica**. IBM's vendor note decomposes the failure into two stages — expired-but-not-yet-purged tombstones, and purged tombstones followed by repair-back [4] (single-source for the two-stage framing — FLAGGED). CASSANDRA-15327 is a documented production instance where the SLA is violated by a *different* subsystem: "Deleted data can re-appear if range movement streaming time exceeds `gc_grace_seconds`," reproducible even at consistency ALL [5].

**Documented mitigation #2 — never reap (Riak `delete_mode=keep`), with an explicit recommendation tied to the delete-then-reinsert case.** Riak's reference doc says: "we recommend setting the `delete_mode` parameter to `keep` if you plan to delete and recreate objects under the same key. This protects against failure scenario cases in which a deleted object may be resurrected" [6]. Cost: tombstones are never reclaimed; the doc also notes backends treat Riak tombstones as regular objects, so "reclaiming disk space is not immediate with respect to delete operations, nor even with respect to reaping" [6]. Riak also documents that reaping is not guaranteed at all: "Successful delete requests do not guarantee successful reaping. If a node fails before its reap timer expires, the reap timer will not automatically recommence upon restart" [6].

**Documented mitigation #3 — make the reinsert causally descend from the delete.** Riak's `deletedvclock=true` fetch option is exactly the "read the tombstone's causal context before re-promoting" pattern: "If you are updating an object that has been deleted — or if an update might target a deleted object — we recommend that you first fetch the causal context of the object prior to updating" [7]. Cost: an extra read round-trip on every write that might target a deleted key, and client cooperation.

**The add-wins/remove-wins framing.** The canonical statement of the consequence of add-wins is Dynamo: "Using this reconciliation mechanism, an 'add to cart' operation is never lost. **However, deleted items can resurface**" [8]. The OR-Set (add-wins, unique-tag-per-add, remove only removes *observed* tags) is attributed to Shapiro/Preguiça/Baquero/Zawirski RR-7506 (2011) [9] — **FLAGGED: I could not fetch that PDF; I confirmed the report's existence, HAL id `inria-00555588`, and canonical URL via search, but I did not read the OR-Set section directly.** Bieniusa et al.'s optimized OR-Set [10] is likewise cited but not read. A production account of switching a shipped sync engine from remove-wins to add-wins, described as a breaking change, is Ditto v4 [51] — **FLAGGED as vendor self-report, single source**.

**"Tombstone GC requires knowing all replicas have seen the delete" — the exact literature term is causal stability.** The precise definition is Baquero, Almeida & Shoker, *Pure Operation-Based Replicated Data Types*, **Definition 5.1**: "A timestamp τ, and a corresponding message, is causally stable at node *i* when all messages subsequently delivered at *i* will have timestamp t > τ" [11]. Crucially, the authors distinguish this from classic message stability: "This notion differs from the classical message stability … in which a message is considered stable if it has been received by all nodes. **Our definition is stronger**, as we also require that no further concurrent messages may be delivered." It is per-node, not global. The stated sufficient condition for the oracle is that node *i* has delivered, from *every* other node *j* ∈ I, some message with timestamp t > τ [11]. Their §7.2 "Causal Stabilization" is the GC mechanism: once a PO-Log entry's timestamp is causally stable, it can be replaced by ⊥ (bottom), "effectively discarding the timestamp," subject to two data-type conditions — queries must be unaffected and the causal-redundancy relations R, R₀, R₁ "must not compare the existing PO-Log timestamps together" [11]. **Stated cost: the oracle requires knowing the full node set I, and requires receiving a subsequent message from every other node.** In an open replica set with churn, that condition is never satisfiable — this is the same constraint Merkle-CRDTs names below.

**The content-addressed restatement of that constraint.** Merkle-CRDTs [14] is the paper that states it for content-addressed stores specifically, and leaves it open: "We leave the topics of DAG compaction and garbage collection for future work, although we intuitively note that **discarding parts of the Merkle-DAG should not be attempted before making sure that every replica is aware of them. This, in turn, requires either having knowledge of the current replica-set or using an external source of truth (i.e. a blockchain), a system constraint that we did not have before.**" This is the single most on-point citation for "safe tombstone GC in a content-addressed replicated store requires an extra, otherwise-unneeded system constraint."

**GC-vs-concurrent-write races are the operational face of the same problem, and are documented as unsolved in at least two major systems.** git-gc(1) NOTES: "when *git gc* runs concurrently with another process, there is a risk of it deleting an object that the other process is using but hasn't created a reference to. This may just cause the other process to fail or **may corrupt the repository** if the other process later adds a reference to the deleted object." Two mitigations are named — an mtime grace period (`gc.pruneExpire`, default 2 weeks; "Any object with modification time newer than the `--prune` date is kept, along with everything reachable from it") and mtime-refresh on re-add — followed by the explicit admission: "**However, these features fall short of a complete solution**, so users who run commands concurrently have to live with [the risk]" [15]. This text was deliberately expanded upstream in commit f1350d0 [16]. Cost of the mitigation: two weeks of retained garbage by default, plus `gc.cruftPacks` (default true) to keep that garbage in a packfile rather than as loose objects [15].

Docker/OCI Distribution states the equivalent and chooses the heavier mitigation: mark-and-sweep over content addresses, with "**You should ensure that the registry is in read-only mode or not running at all.** If you were to upload an image while garbage collection is running, there is the risk that the image's layers are mistakenly deleted leading to a corrupted image. This type of garbage collection is known as **stop-the-world** garbage collection" [28]. The failure is documented as observed, not theoretical [29], and PR #3544 proposes the cheaper mitigation of inverting phase order — enumerate blobs *first*, then mark — so that blobs pushed during a long mark phase are never candidates for sweep [30]. IPFS has the analogous pin-vs-GC races: GC during `add` orphaning the temporary root pin [21], `PinLock` deadlocks between `dag import` and `repo gc` [22].

**Not found / not verified for class 1.** I did not find a named, citable treatment of "DVCS resurrection" as a distinct term of art; git's documented vocabulary is *unreachable* and *dangling* objects [17] plus the gc race [15], not resurrection. Treat any claim about a DVCS "resurrection" literature as unsupported.

### Class 2 — DANGLING / UNRESOLVABLE REFERENCES and CYCLES in content-addressed DAGs

**Acyclicity is by construction only for hash-of-children edges, and both IPFS and the Merkle-CRDTs paper state it as a cryptographic-hardness claim, not a structural theorem.** IPFS docs: "The properties of the hash function ensure that no cycles can exist when creating Merkle DAGs. (Note: Hash functions are one-way functions. **Creating a cycle should then be impossibly difficult unless some weakness is discovered and exploited.**)" [19]. Merkle-CRDTs says the same with the same footnote hedge [14]. The mechanism is stated as a construction constraint: "Merkle DAGs can only be constructed from the leaves … Parents are added after children because the children's identifiers must be computed in advance to be able to link them" [19].

**Inference (mine, labelled as such): a supersession pointer breaks that guarantee, because the argument depends on the parent's digest being computed *over* the pointer.** The acyclicity argument requires that every outgoing edge is included in the preimage of the source node's own hash. A supersession pointer whose target is *not* a child — i.e. record R names digest D of a record that is not in R's hash preimage as a child, and D may be minted later or elsewhere — is not covered by that argument. Two records can each name the other's digest as a supersession target if the pointers are added after the digests exist (e.g. as separate signed edge objects, or in a mutable index), producing a cycle in the supersession relation while the underlying content DAG stays acyclic.

**I did not find literature that names this specific construct ("supersession pointer breaks Merkle-DAG acyclicity"). Treat that as an open gap.** What I did find are three systems that ran into the structural consequence and dealt with it explicitly:

1. **Nix.** Nix store references are *not* hash-of-child (a store path is derived from inputs/derivation, and paths can appear inside the content of the object they name via hash rewriting), so acyclicity is not free. The manual therefore states it as an imposed invariant with a carve-out: "Store objects can refer to both other store objects and **themselves**. References from a store object to itself are called self-references. … **References other than a self-reference must not form a cycle.** The graph of references excluding self-references thus forms a directed acyclic graph" [23]. This is the closest documented precedent for "a content-addressed store whose references are not children must forbid cycles by rule." Nix also states the completeness invariant directly — the **Closure property**: "A store can only contain a store object if it also contains all the store objects it refers to," with the caveat that lazy loading is permitted but "the 'closure property' and immutability in conjunction imply that any such lazy loading ought to be deterministic" [23]. The operational check is `nix-store --query --requisites` (the closure) [24].

2. **OCI Distribution's `subject` field.** This is the closest documented analogue of a supersession pointer: an out-of-DAG, by-digest association from one manifest to another, surfaced through a *reverse* index (the Referrers API). The spec resolves the dangling case by **mandating tolerance**: "A registry **MUST initially accept** an otherwise valid manifest with a `subject` field that references a manifest that does not exist in the repository, allowing clients to push a manifest and referrers to that manifest in **either order**" [32]. And it draws the line explicitly against in-DAG children: "A registry **MAY reject** a manifest uploaded to the manifest endpoint with descriptors **in other fields** that reference a manifest or blob that does not exist in the registry … MUST result in one or more `MANIFEST_BLOB_UNKNOWN` errors" (error code-5, "manifest references a manifest or blob unknown to registry") [32]. **The stated cost of the fallback path** (registries without the Referrers API) is that clients must read-modify-write a referrers index under a well-known tag, and the spec disclaims the race: "**Protection against race conditions is the responsibility of clients and end users**, and can be resolved by using a registry that provides the referrers API" [32]. Docker's older registry had the concrete manifestation: "Manifest deletion can leave dangling tag links" [31].

3. **Git partial clone / promisor objects.** This is the documented pattern for *expected* dangling references, and it is worth copying wholesale. The design notes state the invariant is deliberately broken: "the filtered packfile may contain **trees or tags that reference missing blobs or commits that reference missing trees**" [18]. The mitigation is to *mark* the packfiles whose referents may legitimately be absent (`<name>.promisor`), and define a promisor object as one "that it knows (to the best of its ability) that promisor remotes have promised that they have, either because the local repository has one of its descendants in one of its promisor packfiles, or because another promisor object refers to it" [18]. Consequences propagate through the whole toolchain: "`fsck` has been updated to be fully aware of promisor objects," "`repack` in GC has been updated to **not touch promisor packfiles at all**," and a global `fetch_if_missing` flag controls whether an object lookup triggers a demand fetch [18]. The stated efficiency trade-off is candid: "**For efficiency reasons, no check as to whether the missing object is actually a promisor object is performed**" [18] — i.e. they accept that a genuinely-corrupt missing object will be indistinguishable from a legitimately-absent one at fetch time.

**Diagnosis tooling and the "reachable but missing" bug class.** Git's `fsck --unreachable` reports "objects that exist but that aren't reachable from any of the reference nodes"; `--dangling` reports "objects that exist but that are never directly used"; `--lost-found` writes them out [17]. OSTree's `fsck` "looks for **missing and corrupted objects** and metadata" and, notably, has an option to "**Add tombstone commit for referenced but missing commits**" — an explicit tombstone-for-dangling-reference construct [25]. OSTree also documents the exact bug that arises when reachability is computed without an existence check: issue #1222, "`ostree_repo_traverse_commit` currently includes **missing leaf objects in the returned reachable set** and reports no errors … we keep getting objects incorrectly pruned" [26]. And OSTree distinguishes legitimate incompleteness with a `.commitpartial` marker so that fsck does not report interrupted or `--subpath` pulls as corruption [27] — the same idea as git's `.promisor`.

**IPFS unresolvable-CID surface.** The concrete error text for an incomplete DAG is `error traversing DAG: block was not found locally (offline): ipld: could not find Qm…` [20]. Nix has the analogous complaint that a substituter missing a dependency (i.e. violating the closure invariant) produces an unhelpful error [26 is OSTree; the Nix issue is #12610, see Sources].

**Cycles and mutable pointers.** IPFS's documented answer to "I need a cycle" is to add an indirection layer outside the content-addressed DAG: IPNS provides "cryptographically verifiable, mutable pointers to objects" [48], and the community FAQ frames the direct approach as requiring "two dependent fixed points of hashes" [49] (**FLAGGED: issue-thread, low-medium confidence, not an official spec statement**).

### Class 3 — EPOCH ROLLBACK after key compromise + re-enrollment

**TUF names the attack family precisely and gives client-side checks with section numbers.** The spec's goals section names, as distinct attacks: **Rollback attacks** ("An attacker cannot trick clients into installing software that is older than that which the client previously knew to be available"), **Indefinite freeze attacks** ("An attacker cannot respond to client requests with the same, outdated metadata without the client being aware of the problem"), **Fast-forward attacks** (arbitrarily inflating version numbers so that legitimate future updates look like rollbacks), **Mix-and-match attacks**, and **Vulnerability to key compromises** [33].

The client-workflow checks:
- **§5.3.5 root rollback (strictest form):** "The version number of the new root metadata (version N+1) MUST be **exactly** the version in the trusted root metadata (version N) incremented by one, that is precisely N+1. If the version of the new root metadata file is not N+1, discard it, abort the update cycle, and report the rollback attack." [33] Note this is stricter than monotonicity — it forbids *skipping*, which is what forces the client to walk the whole rotation chain.
- **§5.4.3 timestamp rollback:** trusted timestamp version MUST be *less than* the new one; if equal, "discard the new timestamp metadata and abort the update cycle. This is normal and it shouldn't raise any error." Additionally, the snapshot version listed in the trusted timestamp MUST be ≤ the version listed in the new timestamp [33].
- **§5.5.5 snapshot rollback (includes an anti-deletion clause):** targets versions must be monotone, **and** "any targets metadata filename that was listed in the trusted snapshot metadata file, if any, **MUST continue to be listed** in the new snapshot metadata file" [33] — i.e. removal from the manifest is itself treated as a rollback.
- **§5.3.10 / §5.4.4 / §5.5.6 freeze checks:** each metadata's expiration MUST exceed a *fixed update start time* [33].

**The re-enrollment case specifically: TUF §5.3.11 is the exact precedent.** "**If the timestamp and/or snapshot keys have been rotated, then delete the trusted timestamp and snapshot metadata files.** This is done in order to recover from **fast-forward attacks** after the repository has been compromised and recovered. A fast-forward attack happens when attackers arbitrarily increase the version numbers of: (1) the timestamp metadata, (2) the snapshot metadata, and/or (3) the targets, or a delegated targets, metadata file in the snapshot metadata" [33]. The referenced analysis is the Mercury paper [37]. **The stated mitigation is therefore: on key rotation, deliberately discard the monotonic counter state that the compromised key controlled** — the rollback defence is intentionally suspended across the re-enrollment boundary, because the counter is no longer trustworthy. That is the precise structural answer to "epoch rollback after key compromise + re-enrollment." (There is an open spec issue arguing §5.3.11 is under-specified — "The description of step 5.3.11 is very vague, in particular it does not describe how key rotation detection should [work]" — issue #269, see Sources.)

**Stated cost of TUF key rotation.** §6.1: "When replacing root keys, an application will sign the new root.json file with **both the new and old root keys**." Clients "update to the latest set of trusted root keys, by **incrementally downloading all intermediate root metadata files**, and verifying that each current version of the root metadata is signed by a threshold of keys specified by its **immediate predecessor as well as** a threshold of keys specified by itself" [34]. Cost, concretely: (a) the repository must retain every intermediate root version forever (they are addressed as `VERSION_NUMBER.root.json`), (b) an offline client that has been away for K rotations must fetch and verify K files in order, and §5.3.3 bounds this by an implementation-chosen Y ("Y may be 2^10") [33], (c) each rotation requires a dual-threshold signing ceremony with both old and new keys. Explicit residual risk stated in the same section: "an attacker, who controls the repository, can launch **freeze attacks by withholding new root metadata**. The attacker does not need to compromise root keys to do so. However, these freeze attacks are limited by the expiration time of the latest root metadata available to the client" [34].

TAP 8 (*Key rotation and explicit self-revocation*, v2 2024-03-26, Accepted) and TAP 20 (*Self-revocation*, v1 2024-01-29, Accepted) reduce the coordination cost: TAP 8 "allows a role to change or revoke their key without requiring changes from parties that delegate to that role" [35]; TAP 20's motivation names the cost being removed — "this introduces a **lag** between when a key holder becomes aware of a compromise and when the delegator responds to this compromise" [36].

The freeze-attack term originates in Samuel, Mathewson, Cappos, Dingledine, *Survivable Key Compromise in Software Update Systems*, CCS 2010: "If an attacker can prevent a software update system from learning that updates are available, the attacker can also prevent the installation of security updates … We call this a **freeze attack**" [38].

**Transparency logs: the mitigation is detection-by-consistency-proof plus an external monitoring/gossip cost.** RFC 6962 defines Merkle audit paths (§2.1.1) and **Merkle consistency proofs** (§2.1.2), and Signed Tree Heads; consistency proofs are what make truncation/rollback of an append-only log detectable [39]. RFC 9162 (CT v2.0) states the limitation and the generality: "the logs do not themselves prevent misissuance … they ensure that interested parties … can **detect** such misissuance," and "this is a general mechanism that could be used for transparently logging **any form of binary data**" [40]. Sigstore's Rekor applies it directly: "Auditors can monitor the log for consistency, meaning that the log remains **append-only** and entries are never mutated or removed" [46], with the honest residual "an entry in Rekor provides a **single-party attestation** that a piece of data existed prior to a certain time" [46]. The stated cost is that the guarantee is only as good as the monitoring population — Sigstore names one third-party monitor (Purdue) plus a GitHub-Actions-based `rekor-monitor` [47].

**CONIKS is the closest precedent for per-identity key rotation under an untrusted server, with quantified cost.** Goal **G1: Non-equivocation**: "Because CONIKS providers issue signed, chained 'snapshots' of each version of the key directory, **any equivocation to two distinct parties must be maintained forever or else it will be detected by auditors** who can then broadcast non-repudiable cryptographic evidence, ensuring that equivocation will be detected with high probability" [41]. Stated costs, measured: clients "download about **17.6 kB per day**"; the abstract claims "less than 20 kB per day … even for a provider with billions of users"; auditing costs "a constant **2.5 kB per provider per day**"; the prototype server supports 10 M users with 1% key changes/day on a commodity machine [41].

**SUNDR states the theoretical ceiling and the cost of exceeding it.** Fork consistency: "a dishonest server could cause a fetch by a user A to miss a modify by B. However, either user will detect the attack upon seeing a subsequent operation by the other. Thus, to perpetuate the deception, the server must **fork** the two users' views of the file system" [42]. The bound is stated flatly: "**Fork consistency is the strongest notion of integrity possible without on-line trusted parties.**" Three named mitigations with stated costs: (i) move the consistency server to a trusted machine — "trivially guarantees fetch-modify consistency. The problem is that trusted machines may have worse connectivity or availability than untrusted ones"; (ii) a "**time stamp box**" with permission to write one file, updating "every 5 seconds," so "all users who see the box's updates know they could only have been partitioned from each other in the past 5 seconds" (replicable for BFT); (iii) direct client-client gossip — "If a malicious server cannot disrupt network communication between clients, it will be unable to fork the file system state once on-line clients know of each other" [42].

**Keybase sigchain is the deployed instance of the same two invariants.** "All user signature chains must **grow monotonically, and can never be 'rolled back'**" and "Whenever a user posts an addition to a signature chain, the site must sign and advertise a change in global site state, and these updates are **totally ordered**" [43]. Attacker capabilities enumerated in the absence of those invariants map one-to-one onto this conflict class: "Selectively rollback a user's signature chain and/or suppress updates"; "Fake a 'key update', and append signatures at the end of a user's chain"; "Show different versions of the site state to different users" [43].

**Monotonic-counter rollback resistance: ROTE gives the hard numbers, and they are bad for the naive design.** ROTE defines the **rollback attack** ("the adversary violates the integrity of a protected application state by replaying old persistently stored data") and the **forking attack** ("or by starting multiple application instances") [44]. Its Appendix B measurements of the naive mitigation (bump an SGX monotonic counter per sealed state version) are the most useful cost figures I found:
- increment latency: **≈250 ms (two Dell laptops), ≈140 ms (Lenovo P50), ≈80 ms (Dell Optiplex)**; read 60–140 ms; counter service entirely absent on Intel NUC [44]
- **wear-out at ≈1.05 million writes**, after which *all* counters on the platform fail with `SGX_ERROR_BUSY` [44]
- consequence, stated: "Assuming a system that updates one of the enclaves on the same platform once every 250 ms, counters would become unusable in a few days. Even with a modest update rate of **one increment per minute, the counters are exhausted in two years**. Services that need to process tens or hundreds of transactions per second are not possible." [44]
- also: reinstalling the platform software or removing the BIOS battery deletes all counters; and the counter state likely lives on SPI flash reachable by bus tapping / flash mirroring, so "additional hardware components besides the processor must be considered trusted" [44]
- ROTE's own replacement: distributed counter storage across a protection group with quorum **q = f + u + 1 = (n + f + 1)/2** and a **two-round** write (the paper walks through the single-round attack that sequential enclave restarts enable) [44]. Cost: **≈2 ms update / 1.3 ms read on a LAN (2–4 nodes), 2.98 ms / 2.13 ms at 20 nodes, 654 ms / 342 ms across 2 geographic sites, 1.37 s / 810 ms across 5**; 190 tx/s vs 260 tx/s unprotected vs ~6 tx/s with SGX counters at 1 KB state — "a **20–25% performance drop** in comparison to systems which have no rollback protection" [44]. Guarantee named "**all-or-nothing rollback**" [44].
- ROTE also documents a subtle API-level rollback that is directly relevant to re-enrollment: an enclave restarted with *no* sealed state cannot tell whether this is genuinely its first run or the OS is hiding state, "Recall that the SGX APIs do not allow checking existence of previous counter" — detecting it requires creating and deleting all 256 counters, "an operation that takes two minutes," and "a crash before counter deletion would render that particular enclave permanently unusable" [44].

**Ariadne** [45] is the prior state-continuity paper; its stated goal is that modules "either recover their state from the last stored state, or **fail-stop** on detection of tampering." Its store-then-inc ordering gives crash resilience at the cost that it "allows two executions of the latest input," and it minimizes NVRAM wear with single-bit-flip counter increments. **FLAGGED: I read Ariadne's abstract directly but read its mechanism details second-hand from ROTE §8** [44].

**Not found for class 3.** I searched for a documented Signal or Matrix treatment of "replay an old prekey bundle / roll back a device epoch after re-enrollment" and found only tangential material (Signal's Sesame spec on session/device management [Sources], Matrix MSC4153 on cross-signing enforcement). **I could not find a spec section or paper in either ecosystem that names this attack for the re-enrollment case. Do not cite Signal or Matrix for this without further work.**

## Cross-class synthesis (three transferable design rules, each with a citation)

1. **A grace period is a bet on a repair SLA, and every documented system that took the bet also documents the case where the bet loses.** Cassandra: `gc_grace_seconds` + repair, loses on long node downtime [1] and on slow range movements [5]. Git: 2-week mtime grace, "falls short of a complete solution" [15]. Docker Distribution declined the bet entirely and requires read-only mode [28].

2. **Safe tombstone GC in a replicated content-addressed store requires exactly one piece of information that content addressing does not give you: the replica set.** Stated as causal stability [11] in the CRDT literature, and restated for Merkle-DAGs as an *additional system constraint* — "knowledge of the current replica-set or … an external source of truth" — that the design otherwise did not need [14].

3. **The precedent for out-of-DAG pointers (supersession) is "mandate tolerance of dangling, mark it explicitly, and exempt it from GC."** OCI: the registry MUST accept a `subject` naming a nonexistent manifest, while it MAY reject a *child* descriptor naming a nonexistent blob [32]. Git: promisor packfiles are marked, fsck is made aware, and `repack` in GC does not touch them [18]. OSTree: `.commitpartial` markers plus fsck-added tombstone commits for "referenced but missing commits" [25][27]. Nix: acyclicity of non-self references is an explicit *rule*, not a property inherited from hashing [23].
